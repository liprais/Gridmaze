# Gridmaze 项目升级方案

## 1. 方案摘要

Gridmaze 当前已经具备完整的最小游戏循环：探索迷雾、识别地砖、承受或利用事件、抵达出口并进入下一层。下一阶段不应急着堆叠敌人和复杂战斗，而应沿着现有优势，把游戏明确为一款以**信息、路径和风险选择**为核心的轻量 3D 地牢游戏。

本方案保留“99 层”这一记忆点，将其组织为 **9 个章节 × 11 个微型楼层**：

- 每层保持短小，目标仍是找到出口。
- 每个章节引入一种明确的环境规则。
- 每 11 层进行一次阶段结算，并从三个遗物中选择一个永久强化。
- 玩家可直接寻找出口，也可承担额外风险探索可选奖励。
- 在章节边界自动存档，避免一次失败或关闭页面导致长流程完全丢失。

实施顺序为：**稳定性修复 → 逻辑与渲染解耦 → 11 层纵向切片 → 99 层内容扩展 → 发布打磨**。

---

## 2. 当前判断

### 已有优势

- 12×12 网格和单格移动规则简单，学习成本低。
- 迷雾、指南针和扫描已经形成“信息获取”玩法。
- 回起点、传送和随机地图已经形成“位置风险”玩法。
- 地图生成包含安全路径和连通性检查，基础算法可靠。
- Three.js 场景、动画反馈、中英文和移动端入口已经具备。
- 工程体量较小，仍处于适合重构的阶段。

### 核心问题

1. 99 层之间的差异主要来自权重和雾浓度，缺少真正的新决策。
2. 危险地砖多数只延长路线，没有失败压力或长期代价。
3. 找到出口总是唯一目标，玩家缺少“现在离开还是继续探索”的选择。
4. 游戏状态、输入、规则、动画和 Three.js 生命周期集中在 `main.ts`，继续增加内容会迅速失控。
5. 地图重建没有释放 GPU 资源，长流程与“99 层”目标存在直接冲突。
6. 当前缺少自动化测试，随机地图和事件组合难以稳定回归。

## 3. 产品目标

### 3.1 核心体验

让玩家在每一步都思考三个问题：

1. 我掌握的信息够不够？
2. 这条路线的风险是否值得？
3. 我应该立即离开，还是多探索一点换取长期优势？

### 3.2 阶段目标

| 阶段 | 玩家体验目标 | 工程目标 |
|------|--------------|----------|
| 稳定版 | 连续游玩 30 分钟无明显故障 | 修复输入、i18n、显存和后期雾问题 |
| 纵向切片 | 11 层内出现风险、奖励和一次成长选择 | 建立可测试的纯游戏逻辑 |
| 完整战役 | 9 个章节具有可感知差异 | 内容由配置驱动，支持章节存档 |
| 发布版 | 桌面和移动端均可顺畅完成一章 | 完成性能、可访问性和部署验收 |

### 3.3 非目标

第一轮升级暂不加入：

- 实时战斗、装备栏和复杂数值养成。
- 多人联机、排行榜和账号系统。
- 大量美术资产或写实视觉升级。
- 无限随机模式。

这些内容会稀释当前清晰的格子探索核心，并显著扩大实现范围。

## 4. 核心玩法方案

### 4.1 章节结构

99 层划分为 9 个章节，每章 11 层。每章由统一配置控制：

```ts
interface ChapterConfig {
  id: string;
  floorRange: [number, number];
  fogMin: number;
  fogMax: number;
  tileWeights: TileWeights;
  modifier: ChapterModifier;
  rewardPool: RelicId[];
}
```

首轮只需实现前三种章节规则，验证结构后再扩展：

| 章节 | 楼层 | 主题 | 规则变化 |
|------|------|------|----------|
| 1 | 1–11 | 测绘区 | 标准规则，用于学习所有基础地砖 |
| 2 | 12–22 | 暗区 | 可视范围缩小，扫描和指南针价值提高 |
| 3 | 23–33 | 不稳定区 | 随机地图增加，但会提前一回合给出视觉警告 |
| 4–8 | 34–88 | 后续扩展 | 从传送网络、假信号、局部坍塌等规则中逐章加入 |
| 9 | 89–99 | 深层区 | 混合已学规则，降低随机惩罚，强调综合决策 |

章节差异必须来自**规则变化**，而不只是提高墙壁概率或把画面变得更暗。

### 4.2 可选探索目标

每层除出口外，随机生成一个“数据核心”。

- 抵达出口：立即进入下一层。
- 拾取数据核心：获得 1 个数据碎片，但必须多走一段未知路线。
- 每章结算时，数据碎片用于提高遗物选择质量或恢复一次容错资源。
- 数据核心必须生成在可达位置，且不能位于安全路径的必经格上。

这个设计让“继续探索”成为自愿风险，而不是强制劳动。

### 4.3 容错资源

新增 3 点“稳定度”：

- 触发未被护盾抵消的危险地砖时失去 1 点。
- 稳定度降到 0 时，本章失败并回到该章第 1 层。
- 每章结算恢复 1 点，最大为 3。
- 护盾仍然抵消一次危险，定位保持不变。

危险地砖因此产生长期代价，但失败只回退当前章节，不抹掉整个 99 层进度。

### 4.4 遗物成长

每完成 11 层，从三个遗物中选择一个。首轮实现 6 个即可：

| 遗物 | 效果 |
|------|------|
| 余光 | 初始揭示半径 +1 |
| 完整地图 | 每层首次接近出口时显示方向提示 |
| 稳定锚 | 每章第一次“回起点”不扣稳定度 |
| 传送校准 | 传送不会落在危险地砖或已探索区域 |
| 备用护盾 | 每章开始时获得一次护盾 |
| 深层缓存 | 每三个数据核心恢复 1 点稳定度 |

遗物优先改变规则，而不是简单增加百分比数值。

## 5. 技术架构调整

### 5.1 模块边界

建议把当前 `main.ts` 拆为以下结构：

```text
src/
├── game/
│   ├── engine.ts        # 纯状态转换与事件结算
│   ├── generation.ts    # 地图生成与连通性保证
│   ├── config.ts        # 章节、地砖权重、难度曲线
│   ├── rng.ts           # 可注入随机数和种子
│   ├── save.ts          # 存档版本、读写和迁移
│   └── types.ts
├── scene/
│   ├── dungeon-view.ts  # 地砖、标签、迷雾
│   ├── player-view.ts   # 玩家模型与动画
│   ├── effects.ts       # 闪光、震动、粒子
│   └── dispose.ts       # Three.js 资源释放
├── ui/
│   ├── hud.ts
│   ├── input.ts
│   └── i18n.ts
└── main.ts              # 初始化和模块编排
```

`game/` 不得依赖 Three.js 或 DOM。渲染层只消费状态和领域事件：

```ts
type GameEvent =
  | { type: 'PLAYER_MOVED'; to: Position }
  | { type: 'TILE_REVEALED'; position: Position }
  | { type: 'HAZARD_TRIGGERED'; hazard: TileType }
  | { type: 'FLOOR_COMPLETED'; floor: number }
  | { type: 'CHAPTER_COMPLETED'; chapter: number };
```

### 5.2 随机数可测试化

地图生成函数接收 RNG，而不是直接调用 `Math.random()`：

```ts
generateDungeon(width, height, floor, rng): DungeonData
```

生产环境用随机种子；测试和问题复现使用固定种子。存档中保存当前种子和随机序列位置。

### 5.3 Three.js 生命周期

所有动态对象必须通过统一函数销毁：

- 遍历 `Object3D` 子节点。
- 释放 `BufferGeometry`。
- 释放单个或数组形式的 `Material`。
- 释放材质引用的 CanvasTexture。
- 重建出口信标时同步释放旧资源。

地砖和迷雾优先改为共享 geometry；性能仍不足时再使用 `InstancedMesh`，不作为第一阶段前置条件。

### 5.4 状态与动画

明确游戏阶段，避免多个布尔值互相冲突：

```ts
type GamePhase = 'intro' | 'ready' | 'moving' | 'resolving' | 'choosing-relic' | 'won';
```

逻辑状态先完成转换，动画只负责表现；动画结束后派发完成事件，不在 Mesh 上挂载 `any` 临时字段。

## 6. 分阶段实施计划

### P0：稳定性与体验修复

预计范围：0.5–1 天。

- [ ] i18n 在第一次生成地图前初始化。
- [ ] 切换语言只重建标签和文案，不重置地图、位置、楼层或迷雾。
- [ ] 修复 HUD 楼层文案重复。
- [ ] 输入改成离散动作队列；撞墙时一次按键只记录一次日志。
- [ ] 区分单指移动手势和 OrbitControls 手势，避免同时旋转与移动。
- [ ] 雾浓度改为有上限的曲线，建议范围 `0.015–0.045`。
- [ ] 地图、标签、迷雾和出口信标重建时释放 GPU 资源。
- [ ] 屏幕震动基于原始相机位置偏移，结束后准确复位。
- [ ] README 中 Scan 描述与 3×3 实际行为保持一致。

验收标准：

- 连续重建地图 200 次后，renderer memory 指标回到稳定区间。
- 长按方向键撞墙不会持续刷日志或反复修改 DOM。
- 第 99 层仍能辨认相邻格子、玩家和出口提示。
- 中英文切换前后游戏状态完全一致。
- `npm run build` 无错误。

### P1：纯游戏逻辑与自动化测试

预计范围：1–2 天。

- [ ] 引入 `game/engine.ts`，统一处理移动和地砖效果。
- [ ] 把章节难度、权重和雾参数移入配置文件。
- [ ] 为地图生成注入可设种子的 RNG。
- [ ] 引入 Vitest，新增 `npm test` 和 `npm run test:run`。
- [ ] 为地图生成、移动、护盾和楼层切换建立测试。
- [ ] 将 `main.ts` 收缩为初始化与编排入口。

验收标准：

- 1,000 个固定种子生成的地图全部存在起点到出口的路径。
- 同一版本、同一种子产生完全相同的地图和事件结果。
- 地砖效果无需 WebGL 或 DOM 即可测试。
- 核心规则分支具备自动化覆盖。

### P2：11 层纵向切片

预计范围：3–5 天。

- [ ] 加入稳定度和章节失败逻辑。
- [ ] 每层生成一个可选数据核心。
- [ ] 完成第 11 层后的遗物三选一界面。
- [ ] 实现首批 6 个遗物。
- [ ] 在第 1、4、7 层逐步介绍地砖，不在首屏一次解释全部规则。
- [ ] 增加章节结算，包括用时、步数、碎片和触发危险次数。

验收标准：

- 新玩家无需阅读 README 可完成第一章。
- 直接找出口和探索数据核心是两种都可行的策略。
- 第一章目标时长为 10–15 分钟。
- 玩家至少会在一次遗物选择中面对有意义的取舍。

### P3：99 层完整内容

预计范围：按章节逐个迭代，不一次性完成。

- [ ] 建立 9 个章节配置。
- [ ] 每章至少包含一个规则变化和一个新的视觉提示。
- [ ] 章节 4–8 先通过配置复用现有系统，只有确有新决策时才增加新 TileType。
- [ ] 第 9 章组合前面规则，并降低纯随机造成的失败。
- [ ] 在每章边界保存进度、稳定度、遗物、种子和语言。
- [ ] 存档加入版本号和迁移/失效策略。

验收标准：

- 完整流程预计 60–90 分钟，可跨会话继续。
- 相邻章节在前 2 层内即可感知玩法差异。
- 失败最多回退 11 层。
- 刷新页面不会改变当前地图或丢失已获得遗物。

### P4：发布打磨

预计范围：1–2 天。

- [ ] 增加暂停、重新开始本章、清除存档和音量入口。
- [ ] 支持减少动态效果，降低闪光和屏幕震动。
- [ ] 检查色盲可辨识度，关键地砖不能只依赖颜色区分。
- [ ] 适配 375×667、768×1024 和常见桌面尺寸。
- [ ] 检查首屏加载、移动端帧率和 bundle 体积。
- [ ] 更新 README、操作说明和 GitHub Pages 发布流程。

验收标准：

- 主流桌面浏览器保持稳定 60 FPS；中档移动设备目标不低于 30 FPS。
- JS gzip 体积尽量保持在 150 kB 左右，超出时说明原因。
- 键盘和触摸均可完成完整章节。
- 构建、测试和部署检查全部通过。

## 7. 测试策略

### 单元测试

- 权重随楼层变化符合配置边界。
- 起点和出口合法且始终连通。
- 数据核心可达且不是出口必经点。
- 护盾只抵消下一次危险。
- 稳定度、章节失败、遗物效果正确结算。
- i18n 缺失键具有明确回退行为。

### 属性测试/批量随机测试

- 批量生成不同种子，检查连通性、坐标范围和特殊地砖数量。
- 检查传送目标永远合法。
- 检查任何事件序列都不会产生越界位置或非法阶段。

### 浏览器验收

- 首次进入、开始游戏、移动、撞墙、触发每类地砖。
- 中英文即时切换且不改变状态。
- 桌面键盘、触摸滑动、相机旋转和缩放互不冲突。
- 连续换层、Random Map 重建和章节存档恢复。
- WebGL context、控制台错误和 renderer memory 监测。

## 8. 风险与控制

| 风险 | 表现 | 控制方式 |
|------|------|----------|
| 内容范围膨胀 | 每章都开发全新系统 | 先通过配置和规则组合验证，新 TileType 必须带来新决策 |
| 随机导致不公平 | 玩家无信息地连续受罚 | 危险预警、固定种子复现、限制危险连片 |
| 99 层过长 | 中途退出率高 | 微型楼层、章节存档、失败只回退本章 |
| 重构阻塞玩法 | 长时间没有可玩版本 | P0 独立发布，P1 小步迁移，不进行一次性重写 |
| 移动端性能不足 | 掉帧、发热、触控冲突 | 共享资源、释放 GPU 对象、按实际指标决定是否 Instancing |

---

## 9. 推荐执行顺序

当前只批准并完成 **P0**，发布一个稳定版本；随后实施 **P1 + P2**，得到可完整游玩的第一章。第一章经过实际试玩、确认“额外探索”和“遗物选择”确实有趣之后，再决定是否扩展到全部 99 层。

不建议现在直接制作九章内容。先让 11 层好玩，比先让 99 层存在更重要。
